# Quick Reply Delivery Contract

## 目的

将 Skill 对当前聊天形成的完整判断，
收敛为用户现在最需要采取的下一步结果。

Skill 可以充分理解、判断和分析当前情况。
但 Quick Reply 的最终交付不是完整分析，
而是当前可以直接使用的结果。

## 核心原则

### 1. Skill 可以完整判断

不要限制 Skill 对当前聊天进行必要的理解、判断和分析。
Delivery 不改变 Skill 的判断。

### 2. 最终交付当前最有用的结果

Quick Reply 应从 Skill 已形成的判断中，
选择当前用户最需要看到的主要结果。

通常是：
- 一条可以直接发送的回复；
- 一个明确的"不建议现在回复"判断；
- 一个明确的下一步处理建议；
- 一个必要的沟通方向。

### 3. 不展示完整分析过程

不要把 Skill 的完整：
- 判断依据；
- 事实整理；
- 推断过程；
- 关系阶段分析；
- 多个可能性；
- 长篇解释；

全部转交给用户。

这些内容属于 Skill 的处理过程，
除非当前结果确实需要，
否则不应成为 Quick Reply 的主要交付内容。

### 4. 结果优先

先交付当前结果。
只有当极短的解释对于用户理解或执行这个结果确实有帮助时，
才保留必要解释。

不要为了证明判断有依据而展开完整论证。

### 5. 保留 Skill 的判断能力

不要把 Quick Reply 强制变成单纯的"代写回复"。

如果 Skill 判断当前不应该回复，
可以直接告诉用户不要回复。

如果 Skill 认为应该改变处理方式，
可以直接告诉用户下一步应该怎么做。

Delivery 不得为了生成可发送文本而覆盖 Skill 的判断。

### 6. 一个主要结果

默认让用户能够一眼看出：
> 现在最应该怎么做。

不要同时输出多个平行方案，
不要把不同可能性全部展开。

如果当前 Skill 明确需要同时给出一个判断和一条回复，
可以保留两者，但仍应保持紧凑，
不要展开完整分析过程。

### 7. 保持自然交互

Quick Reply 是直接面对用户的帮助，
不是分析报告。

不要使用：
- "核心判断"
- "事实层面"
- "推断层面"
- "可能性分析"
- "建议"
- "关系分析"

等固定报告栏目。

不要输出完整分析报告。

### 8. 不固定字数

不要要求固定字符数、句数或长度。
结果应该根据当前上下文自然收敛。

### 9. 保持当前 Skill

保持当前 Skill 的：
- 人格；
- 判断方式；
- 专业方法；
- 表达习惯；
- 语言风格。

Delivery 只改变最终交付状态，
不重新定义 Skill 的判断。

### 10. 输出前检查

输出前确认：
- 用户是否一眼知道现在该怎么做？
- 是否已经给出了当前最有用的结果？
- 是否不必要地展示了完整分析过程？
- 是否把判断依据、推断和背景全部倒给了用户？
- 是否仍然保持当前 Skill 的人格？

如果已经有明确结果，
不要为了补充解释而继续展开。
