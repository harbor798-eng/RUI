# Expression & Delivery Contract

## 目的

将 Skill 已经形成的判断、处理结果或建议，
以适合当前 Function 的最终形式交付给用户。

本 Contract 负责"结果如何抵达用户"，
不负责重新决定"应该得出什么结论"。

## 核心原则

### 1. 交付结果，而不是倾倒处理过程

Skill 可以充分理解、判断、举例、解释。
这些属于 Skill 的内部处理过程，不意味着必须全部展示给用户。
默认优先交付已经形成的判断、建议或可执行结果。
只在解释本身对用户理解或使用结果有必要时，才保留最小解释。
不要为了证明判断正确，而自动展示完整的理由、推导、例子或背景分析。

### 2. 保持用户可用性

最终结果应当能够直接支持当前 Function 所要求的任务。
如果结果本身已经足够使用，不要为了展示分析能力继续扩展。

### 3. 不强制固定交付形态

最终结果可根据 Skill 判断采用不同形式，例如：
- 可直接使用的回复
- 简短判断
- 行动建议
- 等待建议
- 处理方向调整

具体形式不由 Delivery 预先规定，而由 Skill 对当前任务的判断决定。

### 4. 区分"Skill 怎么想"与"用户需要看到什么"

Skill 的完整推理链、例子、心理推演、背景分析，是 Skill 的工作过程。
用户最终需要看到的是完成当前任务所需要的最小信息集合。
Delivery 负责从 Skill 的处理过程中筛选出这部分信息。
未被选中的内部推理，不要自动转写到最终回复里。

### 5. 信息密度匹配当前任务

最终交付的信息密度、展开程度和表达复杂度，应与当前 Function 的任务范围相匹配。
不要使用固定字数、固定句数或固定长度作为统一规则。
也不要因为允许解释，就默认把整个思考过程展开。

### 6. 不重新进行判断

Delivery 不负责：
- 重新判断事实
- 重新判断关系
- 重新选择 Skill
- 重新决定策略
- 改变用户目标

Skill 已经形成的判断应被保留。
Delivery 只负责转换为适合用户接收的最终结果。

### 7. 不限制 Skill 个性

Delivery 不规定：
- 人格
- 语气
- 文风
- 词汇
- 表达习惯
- 幽默程度

这些由 Skill 决定。
Delivery 不改变 Skill 的判断方式和人格。

### 8. 不规定机器输出协议

Delivery 不规定：
- JSON
- Markdown
- 字段
- Candidate 数量
- Strategy 数量
- Adapter 格式

这些属于 Output Contract / Output Runtime。

### 9. 不继承历史产品策略

Delivery 不包含任何特定历史产品策略。
特别不包含：
- 3×3 候选
- 自然 / 主动 / 轻微暧昧
- 固定候选数量
- 固定策略集合

如果需要这些能力，应通过独立 Skill 实现。
